### 2.2 Statistical interpretation

- The admission rule and the count class become part of the **configured method** under test: an LLM arm whose late-batch prompt exceeds L\*, or whose count request fails, forfeits under a rule fixed before exposure. This is the same status the existing transport-exhaustion forfeit has. It is asymmetric across arms and must remain so — equalising it (e.g., by re-running) would be selective.
- Illustration only (assumes independent, identically distributed attempt failures across attempts and classes, which is not established and is not measured): if each attempt fails with probability q, a logical call previously failed with probability q³ and now fails with probability 1 − (1 − q³)²; the design adds a second failure opportunity for the LLM arm. It is one more reason an *Excludes* outcome could reflect provider reliability or the admission rule rather than proposer quality. §14.4 must add "admission rejections and count-class failures" to the alternative explanations for a null/exclusion result, and §9.6 must report per block: admission-rejected batches, count-failed batches, generation-failed batches, and the counted input tokens of every dispatched request.
- No decision rule, estimand, interval, margin, stage structure or SVF/IVF logic changes. Non-support remains not exclusion; ties at D = 0 remain on the Excludes side; SVF/IVF still blocks both confirmatory directions. No pre-specified sensitivity re-analysis is added; only descriptive forfeit-cause tabulation.
- Whether a body exceeds L\* depends on the rendered text (values, correction content, formatting tokens), not only on the row count; no claim is made that rejection is confined to late batches or monotone in valid-row count. Rejection is a predetermined function of the request bytes and is not outcome-adaptive in the sense of §13.4, but it is history-dependent; the amendment says so.

### 2.3 Input-affecting projection (SDK 3.9.0 and reference, verified)

Count schema keys (12): `conversation`, `input`, `instructions`, `model`, `parallel_tool_calls`, `personality`, `previous_response_id`, `reasoning`, `text`, `tool_choice`, `tools`, `truncation`. Generation-only keys in the SDK base params (19): `background`, `context_management`, `include`, `max_output_tokens`, `max_tool_calls`, `metadata`, `moderation`, `prompt`, `prompt_cache_key`, `prompt_cache_options`, `prompt_cache_retention`, `safety_identifier`, `service_tier`, `store`, `stream_options`, `temperature`, `top_logprobs`, `top_p`, `user` (plus `stream`). Count-only key: `personality` (accepted by the count endpoint, absent from the create reference as retrieved — an asymmetry that would let a count body carry a style preset the generation cannot; it must be forbidden).

Projection rule: count body = {k: gen[k] for k in gen if k in COUNT_SCHEMA}; the result must be exactly {`model`, `input`, `reasoning`, `text`, `truncation`}; the generation-only remainder must be exactly {`max_output_tokens`, `store`, `stream`, `service_tier`, `prompt_cache_options`}; any other key is a contract violation before any dispatch. `reasoning` carries only `effort`; the SDK also exposes `mode` (`standard`/`pro`), `context`, `summary`, `generate_summary` — all omitted, all read back from the echo. The Cookbook independently states the same split ("Send `max_output_tokens`, `service_tier`, and `store` only with the response request"; same `model` and `input` for both).

### 2.4 Failure classification and overlooked API state

Overlooked in the candidate design and now specified (table in the contract file):

1. **HTTP 2xx is not sufficient for "received model response" under Responses, and every 2xx object is settled (usage charged and preserved, profile validated) before it is classified for retry or parsing.** The object carries `status ∈ {completed, failed, in_progress, cancelled, queued, incomplete}` and an `error` object whose codes include `server_error` and `rate_limit_exceeded`. Rule: `completed` → parse; `incomplete` → received (protocol §7.4 truncation row; `incomplete_details.reason` recorded); `failed` with `error.code ∈ {server_error, rate_limit_exceeded}` → retryable, consumes an attempt; `failed` otherwise → terminal, batch forfeited, no correction; any other status → contract anomaly (impossible with `background:false`), batch forfeited, E9 halts.
2. **Output extraction.** Text is the concatenation of `output_text` parts of `message` items in `output`; a `refusal` part or empty output is a received response with no valid vectors → correction path (§7.3). Reasoning items in `output` are never parsed.
3. **Count payload validity.** `object == "response.input_tokens"` and a non-negative non-bool integer `input_tokens`; anything else is a count contract anomaly.
4. **Rate-limit headers.** `x-ratelimit-limit-*`, `x-ratelimit-remaining-*`, `x-ratelimit-reset-*`, `Retry-After` are documented response headers; they are the only observable account-limit state and must be retained on every count and generation response (and on error responses). Documented TPM consumption is max(`max_output_tokens`, a character-based estimate), so exact counts do not predict rate-limit consumption.
5. **`Retry-After` is a documented minimum wait** — never shortened; see item 3 disposition and the `retry_decision` rule (unknown/non-finite remaining deadline ⇒ no retry).
6. **Credential/billing failures** (401/402/403) on either class → halt LLM dispatch for the run.
7. **`truncation` deprecated** in the reference; `disabled` still default and still the only setting that fails loudly on over-context.
8. **`store:false` is not zero server-side storage or retention** (Cookbook, data-controls reference) — the amendment states it as a limitation and makes no "no server-side storage" claim.
9. **Snapshot identity**: the model page lists a single snapshot `gpt-5.6-sol`; there is no dated snapshot to pin.

### 2.5 Workflow custody and exposure

- Count requests transmit the same prompt bytes as generation; they add no outcome information but double the number of provider-side records. Each count request is logged in `EXPOSURE_LOG.jsonl` as a pre-freeze provider call during E9 and as a study call thereafter; `operational-setup.json`'s `token_count_calls: 0` is the current truth and must be updated by the actual E9 record, not by this review.
- Journal events (re-read before every dispatch, because the runner forks per attempt): halt state and halt class, identity baseline, price validity, count receipts keyed by count-body SHA-256, reservations for both classes, and the bound canonical request bytes journaled **before** dispatch so a process kill after dispatch leaves an auditable record (Codex's durable request-record module reports 19 offline tests including killed-writer retention — Codex's statement, not rerun here). Retained headers exclude request authorization material. Raw count and generation responses (body and headers) go to the protected `raw/` directory; the count receipt hash enters every generation log row.
- No independent evaluator blinding is created or claimed; automated locked sequencing is unchanged.

## 3. The admission limit L\*: critique and selection

The rev-1 candidate fixed L\* = 200,000. Three documented boundaries exist for `gpt-5.6-sol`: 272,000 input tokens (price-tier boundary: "Prompts with >272K input tokens are priced at 2x input and 1.5x output for the full request"), 922,000 (maximum input tokens), 1,050,000 (context window; L\* + 8,192 must fit). 200,000 coincides with none of them.

**Selection (Codex, prospective, before any count observation): L\* = 272,000**, read conservatively as 272,000 rather than 272×1,024, on Claude Science's rationale that it is the largest limit under which every admitted request has a single documented price schedule and that it reduces design-induced size rejections. It is an admission choice, not a proof that every legal history fits, and not spending authority. **200,000 is retained as the superseded proposal** (a round, budget-driven cut below the price boundary; it lowers the a priori ceiling from 5,708.39 to 4,395.11 USD at n = 4,560, promo rates, at the cost of more admission forfeits).

Corrections to rev 1's argument, per Codex: a higher limit is not scientifically free — it changes the admitted method and resource allocation and the exposure to per-attempt latency and deadlines, while reducing size rejections; and whether a body exceeds the limit depends on the rendered text, so no claim about late-batch-only or monotone rejection is made. L\* is fixed in the amendment before E9; if an E9 fixture count exceeds it, that is a recorded finding requiring a revised amendment, not a silent adjustment. No token count exists for any fixture today (the Sol tokenizer is undocumented; tiktoken vocabularies are outside the sandbox allowlist), so no estimate of where F2 (103,146 B combined text) falls is offered.

## 4. Genuine blockers and their gate

Writing and adopting the prospective technical amendment is not blocked by any of the following; **live dispatch (E9 gate) is**:

1. **Count-endpoint billing evidence.** Account/provider contract evidence covering charges for count requests, including failed and rejected counts, and the applicable model rates — or an explicitly adopted and bounded financial-risk exception, which is not proposed or adopted. Prospective scenarios can be written now; four E9 observations or delayed daily Costs totals cannot prove a fee maximum or free counting.
2. **Account tier and limits** (operational context): usage tier, monthly usage limit, `gpt-5.6-sol` RPM/TPM. Documented tier limits are below or near the study ceilings and can make a calendar-month two-stage run infeasible regardless of the software cap.

## 6. Explanations (project communication rule)

**Technical.** Every LLM request is first sent to the provider's counting endpoint, which returns the exact number of input tokens the model will receive for that payload. If the count exceeds a limit fixed before the study, the request is not sent and the batch is forfeited under the existing failure contract. The generation request is byte-identical on all input-affecting fields, so `usage.input_tokens` must equal the count; inequality means the provider changed something and blocks confirmatory interpretation. Model identity is evidenced by the generation response's echoed settings and model string — validated against the frozen profile before any baseline is accepted — rather than a fingerprint, which the inspected endpoint does not provide; the count response carries no model field.

**Layperson.** Before each paid question to the AI we ask the provider "how big is this question?" and refuse to send anything bigger than a size we chose in advance. That makes the spending cap a fact we enforce rather than a guess about how text turns into tokens. The price we pay for this is that the AI arm now has one more way to lose a turn, and that we can only verify the AI is "the same model" by checking the labels it sends back, not by any deeper signature.

**Commercial relevance (speculative).** Exact pre-flight token counting with client-side reservation is the per-request cost control the inspected provider documentation supports; any product built on paid LLM optimisation loops would need the same machinery. Nothing here bears on whether the AI arm performs better.

**Flaws and alternatives.** A null or exclusion result could be produced by admission or count-class forfeits rather than proposer quality; a support result could rest on provider stationarity that cannot be verified under a single undated snapshot. Effective sampling settings remain unobserved when echoed as null. Another provider or contract route may exist that the retrieved documentation does not show.
