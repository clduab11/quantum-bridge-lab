# Assessment of the prospective contract-resolution proposal — 2026-09-08

**Status:** independent technical critique by Claude Science of Codex's proposal (counted Responses requests with count-to-send body identity; a frozen numerical admission limit; redefining the studied method as archived request profile plus observable response metadata). The proposal is **not adopted** here; protocol v0.4 (`0df9242f…3eda5`) is unchanged and unfrozen. Any adoption requires an explicit pre-exposure amendment with new fixtures and its own review. No live call was made for this assessment; every statement about the API comes from documentation retrieved 2026-09-08 (`responses_create.html` SHA-256 `558be3cd…`, `input_tokens_count.html` `daeb6076…`, `token_counting.md` `c60315cf…`, plus the files already listed in the contract document).

## 1. What the documentation supports and what it does not

| Claim needed by the proposal | Documentation status |
|---|---|
| A count endpoint exists that takes the same payload as generation | Yes: `POST /v1/responses/input_tokens` "accepts the same input format as the Responses API" and "returns the exact count the model will receive", including "formatting tokens used to represent request structure" |
| The count applies to a **Chat Completions** body | **No.** The endpoint is Responses-format only. Count-to-send identity therefore forces the generation request itself onto `POST /v1/responses`. This is a change of endpoint relative to the current candidate contract, not an add-on |
| The count is exact for the model that will generate | Documented as the count "the model will receive" for the same payload; the count body carries `model` and `reasoning`, so effort and model can be held identical. Whether the count is stable across time (provider-side tokenizer changes) is not documented |
| The count request is free | **Not documented.** No pricing row exists for the count endpoint; its billing, rate limits and retry semantics are unknown and must be budgeted, capped and deadlined like any other request (the proposal already says so; this assessment concurs) |
| Responses supports Sol | Yes: model page lists `v1/responses` as Supported |
| Responses returns `system_fingerprint` | **No field exists** in the Responses reference (0 occurrences). Under Responses the §6.1 "model fingerprint" requirement is structurally unsatisfiable, not merely unmeasured |
| Responses returns usage with cache categories | Yes: `usage.input_tokens`, `input_tokens_details.{cached_tokens, cache_write_tokens}`, `output_tokens`, `output_tokens_details.reasoning_tokens` |
| Statelessness controls | `store` **defaults to true** on Responses (must be sent `false`); `previous_response_id`, `conversation`, `context_management`, `truncation` exist and must be omitted or fixed (`truncation: "disabled"` so an over-limit input errors rather than being silently truncated); `reasoning.effort` accepts `none|minimal|low|medium|high|xhigh|max` |
| Sampling parameters | `temperature`/`top_p` are documented Responses parameters, but whether Sol accepts them or what its effective values are is still undocumented — the same gap as under Chat |

## 2. Critique

**(a) The counted admission limit is scientifically sound as an *enforcement* device and honest about what it does not prove.** Freezing a numerical admission limit L\* and rejecting any counted body above it before generation makes "every dispatched request had ≤ L\* input tokens" a *verified* property of the run rather than an inference from bytes. It does not claim that every legal 200-row history fits, and it should not: an over-limit history becomes a forfeited batch under §7.3 (recorded as `client_error`, no correction), which is procedurally identical to the existing forfeit path and does not favour any arm. The financial cap then follows from L\* and the output cap without any tokenizer hypothesis. This is the first tokenizer-independent route to a defensible per-attempt ceiling I have seen in this project; Tier B remains a hypothesis and is not rescued by it.

**(b) The cost is a second request class with its own unknowns.** Each logical call needs a count request before the generation request; retries reuse the identical counted body (count once per distinct body, not per attempt). That adds 760 (or 1,520 with corrections) count requests whose billing, rate limits and failure modes are undocumented. They must appear in the budget as attempts with their own reservation (unknown price → the record must carry an explicit assumed rate or reserve), their own cap and deadline, and their own ledger scope. Count failure must map to a defined outcome (recommend: treat as transport failure → retry within the existing 3-attempt budget; unresolved → forfeit), fixed prospectively.

**(c) The endpoint move changes the identity evidence available, and that is the substantive scientific cost.** Under Responses no fingerprint exists. The proposal's second part — defining the studied method as *archived request profile + observable response metadata* (`model`, `service_tier`, usage, response id, retained raw bytes) — is the only honest description of what can be observed. It is scientifically valid **only if** stated as a reduction in the identity standard: stationarity of the provider is then an untested assumption, drift can be detected only through `model` string changes or usage anomalies, and "reproducibility" means transcript-level reproducibility (anyone can see exactly what was sent and received), not re-executability. The IVF rule for observed identity change stays; but undetectable drift is now acknowledged as possible. This must be written into the amendment as a limitation of the confirmatory claim, not buried in a methods note.

**(d) What the proposal does not fix.** Effective sampling values remain undocumented on both endpoints; the amendment should state that the studied configuration is "the provider's undocumented default sampling at fixed `reasoning.effort`" and that this is an unrecorded nuisance variable. The 200-row worst-case wording in G-MODEL is replaced by "admission-limited" wording, which is a genuine protocol change and must be reviewed as such. New fixtures are required (Responses-format bodies; a count-only fixture; an over-limit fixture that must be **rejected** before generation).

**(e) Consistency checks the amendment must require before exposure.** (i) For every fixture, count-then-generate and require `usage.input_tokens == counted input_tokens`; any mismatch is a contract failure that halts. (ii) `store:false`, `truncation:"disabled"`, no `previous_response_id`/`conversation`/tools, explicit cache mode with zero breakpoints, `cached_tokens == cache_write_tokens == 0` observed. (iii) The count body and the generation body must be byte-identical except for fields that exist only on generation (`max_output_tokens`, `store`, `service_tier`, `stream`); the pre-send hook already built for Chat generalises directly. (iv) The count request's own retention, ledger scope and halt policy.

## 3. Decision recommendation

1. **Do not accept Tier B as a verified bound** (unchanged). It stays a conditional planning hypothesis.
2. **Pursue the counted-admission design as a prospective amendment candidate**, explicitly separate from frozen v0.4, with the identity-standard reduction stated as a limitation. I assess it as scientifically valid: it converts the input ceiling from inference to enforcement, keeps the forfeit path symmetric across arms, and is honest about what it cannot establish (fingerprint, effective sampling, undetectable drift). It is the smallest evidence-backed way through the G-COST/G-MODEL requirements that does not weaken them silently.
3. **Sequence:** (a) draft the amendment text and new fixtures offline (Responses-format adapter variant with the same enforcement machinery; count-only fixture; over-limit rejection fixture); (b) reviewed pre-exposure amendment recorded in `AMENDMENTS.md`; (c) only then a capped E9 authority record covering **both** request classes (count and generation, each budgeted at an explicit assumed rate with reserve); (d) E9 must show the count/usage equality in (e)(i) on every fixture before any freeze.
4. **If the amendment is rejected**, the alternative is the existing Chat candidate with the identity requirement unmet as written and L only hypothesised — i.e. stop before paid exposure. There is no third route in the retrieved documentation.

Retained disagreement to record: this assessment treats the absence of a fingerprint field on Responses as a *structural* limitation to be declared, whereas one could argue the Chat fingerprint (deprecated, nullable) was never meaningful evidence either; both positions should be visible to the amendment reviewer. No independent evaluator blinding is claimed under either endpoint.
