## 3. Input-token ceiling: what is documented, what is hypothesis

The calculator needs `input_token_ceiling` L. There is no Chat-format counting endpoint and the Sol tokenizer is undocumented. Every L below is therefore a **conditional planning hypothesis**; none is a verified universal Chat token ceiling, and **none satisfies protocol §7.2 (frozen tokenizer-derived L_in) or G-COST/G-MODEL as written**. The context-fit gate is kept separate from any financial scenario and stays open in every tier.

- **Tier A — documented request maximum (conditional).** The model page documents "Maximum input tokens: 922,000". The scenario assumes (i) the endpoint enforces that admission limit, (ii) no accepted request is billed for more input than it contains, (iii) rejected/oversized requests are not billed (undocumented), and (iv) the long-context rate row applies. Under those assumptions a per-attempt token charge cannot exceed (922,000 × $10 + 8,192 × $30)/1e6 = $9.46576. It is a conditional envelope, not an unconditional bound and not a planning figure.
- **Tier B — 272,000 price-threshold hypothesis (conditional).** Hypothesis: the two ASCII message texts total ≤103,449 B (renderer maximum) or ≤108,835 B (200-row boundary); a tokenizer partitioning bytes cannot yield more text tokens than bytes; provider wrapper/formatting tokens are additive and far smaller than the ~163,000-token headroom to the 272,000 threshold. Spare byte-to-token headroom and a price threshold **do not prove** the provider's wrapper or token counts; the hypothesis is falsifiable only by observed `prompt_tokens` (E9 gives four observations, not a maximum). Tier B is offered for planning only and is **not recommended as satisfying G-COST**. Per attempt (272,000 × $5 + 8,192 × $20)/1e6 = $1.52384.
- **Tier C — byte figure relabelled as tokens plus a margin (illustrative only, NOT a bound).** L = 110,000. Shown for sensitivity; must not be used for authority.

**Rate conventions (point 5 of the review):** the input rate in each scenario is the **full cache-write price** ($5.00 = 1.25 × $4.00 in the ≤272K row; $10.00 above), i.e. every input token is priced as if written to cache. This matches the caching guide's arithmetic (one write plus one read = 1.35× ordinary input: 1.25 + 0.10), so cache-write is a replacement price, not an additive 2.25× charge; ordinary uncached input ($4.00) and cache reads ($0.40) are both below it, so the convention covers every documented input category. Reasoning is inside the inclusive output price and is not counted twice. What the convention does **not** cover: billing categories absent from the retrieved documentation, charges for failed/rejected requests, token-count requests, taxes, and account adjustments — these are unknown and are never assumed zero; they require an explicit nonzero reserve or account evidence.

## 5. Stop conditions (monetary and price validity; scientific rules unchanged)

1. **Price validity is checked before every transport dispatch** — first attempts, retries within a logical call, correction calls and requests inside an already started block alike. If the wall clock is past `price_valid_through_utc`, the request is not sent (`PriceValidityExpired`; runner `client_error` → forfeit path). The documented minimum promotional window ("at least through November 21, 2026") is the only dated fact; the rate after that instant is **unknown**. Historical rates (e.g. 5/30) are stress scenarios, never a guaranteed future rate.
2. A new-rate or expiry amendment (new record with new rates, validity instant and ceiling) must be **fixed prospectively, before any outcome exposure**, and recorded in `AMENDMENTS.md` as `pre-exposure`; it can never be written after seeing results.
3. Before each attempt the ledger must hold ≥ one full per-attempt cap of unreserved authority and be below the attempt cap; otherwise the request is not sent (`MonetaryCeilingReached`), the batch is forfeited without correction, and the arm continues to its next batch. Never mid-attempt; never a retry.
4. Reconciliation frees only the difference between the full cap and priced **fully known** usage; incomplete usage keeps the full cap; overruns (prompt > L, completion > 8192, nonzero cache category, priced > reservation) halt all further dispatch (`LedgerHalted`) and are recorded unclipped.
5. Total attempts are structurally capped at 4,560 by the runner; the coordinator forbids replaying any (block, arm).
6. SVF/IVF conditions follow protocol §7; money is never a reason to rerun or replace.
