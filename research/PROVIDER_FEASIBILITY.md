# Provider feasibility evidence — 2026-09-08

Status: research only. No provider selected, credentials inspected, API generation or token-counting request sent, price negotiated, or spending approved. This report compares two plausible API candidates; it does not equate either API with the Codex or Claude Science user interface. Protocol v0.4 is unchanged and G-MODEL, G-TRANSPORT and G-COST remain open.

## Decision that the evidence supports

Continue with an offline, provider-neutral cost/contract implementation and prepare a synthetic E9 plan. GPT-5.6 Sol is the lower published-cost candidate of these two; Claude Fable 5.1 has especially clear published semantics that its dateless model ID pins a release. Neither is ready to use in the confirmatory study. The next decision should resolve the exact identity/defaults contract and a concrete tokenizer-derived input ceiling before money is authorized. Do not infer experimental performance from the model marketing descriptions or choose an effort level using objective outcomes.

The 8192-token design cap is an important feasibility risk: both candidates charge hidden reasoning within the same output allowance. This cap does not mean 8192 tokens of JSON remain available. A format-only E9 test may establish interface acceptance and example compliance; it cannot prove success on every later history. Changing the cap or prompts after observing study performance would change the protocol.

For a simple auditable initial contract, explicitly disable prompt caching where supported. OpenAI documents `prompt_cache_options: {mode: explicit, ttl: 30m}` with **no** explicit breakpoints as making no cache reads or writes; omit prior-response/conversation links and tools. This is a candidate request configuration, still requiring adapter tests and E9. Anthropic caching uses `cache_control` at top level or on blocks; omit both, and send no prior thinking/tool loop. Verify actual category counts; do not turn an unreported category into measured zero. An ordinary-input-only Sol budget is unsafe if implicit cache writes remain enabled.

OpenAI usage has inclusive `input_tokens` and read/write subsets in `input_tokens_details`. Ordinary input is `input_tokens - cached_tokens - cache_write_tokens`. Claude usage uses distinct `input_tokens`, `cache_creation_input_tokens`, and `cache_read_input_tokens`; total input is their sum, with cache creation further split by TTL. In both, reasoning/thinking is a subset of inclusive output, so charging inclusive output plus reasoning again would double count. Reject inconsistent or unknown category mappings before calling a budget exact.

Sources: [OpenAI cache controls and billing calculation](https://developers.openai.com/api/docs/guides/prompt-caching), [Claude Messages usage](https://platform.claude.com/docs/en/api/messages/create), [Claude thinking cost](https://platform.claude.com/docs/en/build-with-claude/thinking-steering-and-cost).

Let `L` be a **still-unverified** full-request input-token ceiling and `R` the applicable conservative input rate. A protocol-only upper arithmetic bound for both stages is `4560 × (L × R + 8192 × output_rate) / 1,000,000`. The scheduled no-correction/no-transport-retry path uses 760 in place of 4560. This formula is conditional on a single provider generation per dispatched attempt, no tools or added service fees, the output cap encompassing all billed generation, a correct input ceiling/rate and full reservation for uncertain attempts. Add separately authorized E9/counting costs; this is not an approval request or measured workload forecast.

For illustration only, if a later verified ceiling were 50,000 tokens and caching were demonstrably disabled, Sol arithmetic would be $276.5184 for 760 capped attempts and $1,659.1104 for 4560; Fable 5.1 would be $691.2960 and $4,147.7760. These deliberately assume every attempt consumes the entire input and output cap. They do not establish that 50,000 is sufficient, predict realized costs, or include account-specific charges. If Sol cache writes are allowed and all input is reserved at $5 instead, its illustrative figures become $314.5184 and $1,887.1104.

## Transport implementation consequences

Both official Python SDKs default to automatic retry policies broader than this protocol. Explicitly use `max_retries=0` and let the study runner alone decide the three attempts and 5/20 second backoffs. A scalar SDK timeout is not a substitute for the existing outer 300-second wall-clock process boundary: connection/read/write phases and retry handling are distinct. Keep the 36,000-second arm deadline outside the adapter too. Record success and error request IDs, raw response bodies, HTTP status and response metadata before parsing; missing usage on a timeout/error remains unknown and the full reservation remains consumed until reconciled. Local process cancellation does not demonstrate server-side cancellation or refund.

OpenAI `service_tier: default` documents standard processing; omission defaults to `auto` and may use project configuration. Record the returned actual tier. Freeze first-party endpoint, SDK and transport package versions, API version/header semantics, explicit request fields and stateless construction. For Claude, preserve the documented `anthropic-version: 2023-06-01` contract plus pinned SDK and captured model-specific docs; the header date alone is not a promise that all serving behavior is immutable. Do not add model fallback on refusal or error: the study specifies exactly one model.

Source evidence: Context7 resolved `/openai/openai-python` and `/anthropics/anthropic-sdk-python`; one focused query each returned official SDK retry/timeout/request-ID guidance.
