# Separate count and generation budgets — prospective, not adopted

The counted-admission proposal introduces two request classes. The original generation allowance remains 4,560 attempts across both stages; counting can add up to 4,560 attempts. The proposed four-fixture E9 has up to 12 attempts of each class. That is **9,144 network attempts including E9**, not 4,572. These are maximum allowances, not a prediction of how many calls will run or finish within the fixed deadlines.

The existing 36,000-second arm deadline would include both classes. The proposed E9 monotonic stop limit is 7,400 seconds; overhead and any longer server-directed retry waits consume part of it. With only the fixed 5/20-second backoffs, the nominal timeout/backoff sum is 7,400 seconds before overhead. That sum is not a completion guarantee or a bound once longer waits are allowed. Count failures affect the LLM arm specifically and must remain visible in its outcomes and costs.

`qbridge.count_budget.calculate_counted_budget` calculates these classes separately without making any network request. All seven inputs are explicit. `count_attempt_fee_ceiling_usd=None` means the count price is unknown: both the count subtotal and combined total remain null, even if another reserve is supplied. A returned `input_tokens` value measures the planned generation input, not the count request's own bill.

For the initial proposal L*=200,000, illustrative generation rates of 5/20 USD per million and 12 E9 attempts per class, the generation-only maximum is 5,321.07648 USD. Supplying a **hypothetical** fee ceiling of 0.10 USD per count attempt adds 457.20 USD, producing a conditional combined ceiling of 5,778.28 USD rounded upward. That fee would need verification before use. An explicit zero fee is also only an assumption. No count fee has been established in this phase; the default scenario deliberately has **no numeric combined ceiling**.

Following independent Claude Science review, Codex selected **L*=272,000 for the prospective amendment**, before any count observation. This follows the documented ordinary-price boundary and reduces size rejection relative to the initial 200,000 proposal. It changes the admitted method and its resource allowance; it is not a tokenizer-derived bound on every legal history. At the retrieved promotional 4/20 rates, the generation-only allowance is 5,708.3904 USD for both study stages plus 15.02208 USD for E9. Their sum is 5,723.41248 USD; count fees remain unknown. These maxima are not expected spending. The old 200,000 scenarios remain as labeled arithmetic examples; the new 272,000 scenario is also stored in `scenarios.json`.

None of these calculations verifies billing, admits a request, chooses a provider finally, adopts an amendment, authorizes money or freezes the study. Additional account charges and rate validity still require evidence. The original v0.4 calculator and its source remain unchanged.

Validation: 13 new tests and the existing 59 budget tests pass (72 total). Checks cover unknown fees, distinct E9 allowances, exact arithmetic, rounding, explicit-zero limitations, hostile Decimal context and invalid count-specific inputs. No experimental model, token-count or study-objective calls occurred. `scenarios.json` contains the reproducible examples; `verification.json` records their exact checks.

## Primary-source reconciliation

Context7 was queried again for the official OpenAI Python library, and Exa returned five results (including two URL variants of the same counting guide). The [counting guide](https://developers.openai.com/api/docs/guides/token-counting) supports counting complete Responses input. The [spending-controller example](https://developers.openai.com/cookbook/articles/per_run_spending_controller_responses_api) supports per-run reservations but explicitly limits its scope to model-token costs and uses fabricated prices; it does not establish count requests are free or supply actual account terms. Its limits also caution that project-level limits and alerts are not immediate per-request enforcement.

Context7 included a beta count route. Direct inspection of the installed official SDK 3.9.0 confirms `resources.responses.input_tokens.InputTokens.count` posts to `/responses/input_tokens` without a beta query parameter. The count schema includes `model`, `input`, `reasoning`, `text` and `truncation`, among other fields; generation-only fields must be excluded from the count request. This exact installed-source check takes precedence over a cached example. The independent Claude Science amendment review is considering the request projection and observable identity requirements.
